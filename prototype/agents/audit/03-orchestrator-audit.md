## Findings

1. **Delegation and sequencing.** Launch prompts are long (1.3k-9.6k chars) and carry rules well (no commit/push, no thresholds lowered, rebuild bundle). Good: "READ FIRST" lists, invariants lists (27 assets, NW>=125M). Gaps: no run/time budget, no mention of sibling agents (a74ba5), impossible requirement (subagent review for ad0bb9), "known flaky" lists that teach agents to dismiss failures, no acceptance example for ambiguous semantics.
2. **Concurrency handling.** Rule "NEVER run two graders at once" was written into prompts after the collision incidents, but the orchestrator itself broke it (see pattern 1) and launched a74ba5 and abd0ce in parallel on shared files (03:22 and 03:27). It then queued 12 user requests behind them ("three agents edit the same files"), which is correct for safety but means the user waited ~70 minutes for nothing shipped. Better: serialise at launch, or give each agent a git worktree.
3. **Ambiguity.** AskUserQuestion was used well on 11-14 (today's dollars, HOA) but the credit-line semantics (11-10) and the "is there a way to automate this?" question (11-16 03:21) were answered by building. Four of the user's repeated corrections trace to this.
4. **Reporting accuracy.** Relays of agent claims were accurate to the hand-back text. It did not catch that acc7e5's hand-back arrived 16 minutes early, and started its own grader at 20:48:55.
5. **Commit/push/publish hygiene.** Pushes go to the dev branch with main protected (good), but 127 pushes and frequent "Regenerate grader reports" commits make history noisy; hook-created WIP commits include other agents' half-done files; an agent (aeba2d) had to ask whether the WIP commit was its own.
6. **Token/time efficiency.** Orchestrator spent ~$66 mostly on cache reads of a 300k-890k context. 270 notification wakeups; 23 surplus hand-backs. Compactions at 11-09 16:10, 11-10 18:26, 11-12 15:55.
7. **User friction signals.** "Continue?" x3 (rate limits), "!!!!!! Do this first !!!" (11-10 08:24), "Like I said every asset..." (11-10 20:25), and the user's own request for this audit.

## Improvements (orchestrator)
- One writer per working tree: launch implementers serially, or use `git worktree add` per agent; reviewers (read-only) may run in parallel.
- Never run a grader yourself while an agent that grades is active; read the agent's last log instead.
- Wait for the agent's final hand-back (count duplicates); require agents to hand back exactly once.
- For any "can you / is there a way" question: answer, give a 3-line plan with scope, wait for go.
- Keep a requirements ledger (one worked example per user rule) and paste it into every prompt.
- Do not push snapshots of failing work; commit only after the agent hand-back and a green full run.
- Provide a run budget (e.g. at most 10 slices + 1 full) and a mutation canary for any new grader.
